# Vero VR-N76 — Field Notes

Findings from a first successful benlink session against a **Vero VR-N76**
(firmware ~0.7.x, HW ver reported by device) using BLE on **macOS 26.5 (Tahoe)**
with `bleak` via CoreBluetooth. Contributed by KC9MHE, 2026-07-03.

## What worked

- **BLE connect** via `RadioController.new_ble(<peripheral-uuid>)`
- Read: `device_info`, `status`, `settings`, `battery_level`, `channels`
- Write: `set_channel(...)` for name, RX/TX freq, CTCSS tones, bandwidth,
  `tx_disable`, `scan` — all round-tripped correctly and persisted after
  power-cycle.
- ~32-channel table on the currently-selected region parsed cleanly.

## What broke (and how)

Every parse crash was a strict `_pad: t.Literal[0]` field. The N76 sets
non-zero bits in several of them, presumably because Vero's firmware carries
capability flags that upstream benlink hasn't mapped yet.

| Struct       | Field  | Width | Observed value | File |
|--------------|--------|-------|----------------|------|
| `DevInfo`    | `_pad` | 2 bit | non-zero (exact value not captured; pre-refactor 4-bit field observed `4`) | `dev_info.py` |
| `Status`     | `_pad` | 2 bit | non-zero | `status.py` |
| `RfCh`       | `_pad` | 4 bit | non-zero on some channel entries | `rf_ch.py` |
| `SetPhoneStatusBody` | `_pad`/`_pad2` | 1 / 14 bit | not yet exercised — loosened defensively | `phone_status.py` |

**Fix applied in this branch:** each `_pad` was changed from
`t.Literal[0] = bf_lit_int(N, default=0)` to `int = bf_int(N, default=0)`.

Reads still succeed (extra bits are silently accepted). Writes still emit
zeros in those bit positions, matching the pre-existing protocol assumption.
When the maintainer eventually reverse-engineers what those bits mean, they
can be extracted as named `bool`/`int` fields without breaking existing
callers.

## macOS quirks worth documenting

1. **CoreBluetooth uses peripheral UUIDs, not MAC addresses.** The physical
   MAC that the radio advertises (`38:D2:xx:xx:xx:xx` in this case) will
   *not* work as an argument to `RadioController.new_ble()`. Discover with
   `BleakScanner.discover()` and use the UUID it returns
   (`XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX`).
2. **Classic BT pairing hides BLE ads.** The N76 advertises as a
   Handsfree/Headset device on Bluetooth Classic (used for the wireless-mic
   accessory audio). If you pair it via System Settings for classic BT,
   CoreBluetooth may filter its BLE advertisement out of the discovery scan.
   **Unpair the classic connection** before scanning with `bleak`.
3. **BLE authorization is per-process on macOS.** Terminal, iTerm, VSCode
   etc. each need their own "allow Bluetooth" grant. SSH sessions inherit
   no grant and get `BleakBluetoothNotAvailableError: DENIED_BY_UNKNOWN`
   — run locally, not over SSH.
4. **The radio must be BONDED before any write succeeds, and bonding needs
   a foreground GUI app.** Verified KC9MHE, 2026-09-15 (fw 147). The write
   characteristic `00001101-d102-11e1-9b23-00025b00a5a5` requires
   encryption, so the very first frame `_hydrate()` sends fails on an
   unbonded link. CoreBluetooth has no explicit pair API — it "auto-pairs"
   only when something touches an encrypted characteristic, and it draws
   that prompt **only for a foreground application**. Run the same code from
   a background daemon (launchd, a service, an agent runner) and you loop on
   ATT errors forever with no dialog on screen. Run it from Terminal.app.

   Read the ATT error as a progress signal:

   | Error | Meaning |
   |-------|---------|
   | `(15) Insufficient Encryption` | no bond; handshake never started |
   | `(5) Insufficient Authentication` | handshake **started**, radio wants auth — keep the connection open and accept the prompt |

   Two traps while probing for this:
   - The indicate characteristic (`...1102...`) does **not** require
     encryption. Subscribing to it succeeds instantly on an unbonded link,
     so it is a **false positive** for "bond established". Probe with the
     write characteristic.
   - Probe with a real read-only frame, not a filler byte. benlink's own
     `GetDeviceInfo` serializes to `0002000403` and is safe to replay; a
     raw `0x00` is a malformed frame.

5. **Pairing mode self-times-out in ~30–60s, and advertising ≠ pairable.**
   The radio keeps advertising after pairing mode lapses, so a scan can
   "find" it and still fail to bond. Enable pairing mode *first*, then start
   the script — a 12–20s discovery scan otherwise eats most of the window.
6. **Post-bond the radio stops advertising**, and a bonded-but-idle radio is
   also unreachable by direct peripheral UUID
   (`BleakDeviceNotFoundError`). Re-enable pairing mode for a later session.
7. **Peripheral UUIDs go stale.** They are per-host *and* change across
   unpair/re-pair, so a hardcoded constant silently stops matching. Match on
   the advertised name `VR-N76` and keep the UUID as an override only.

## RFCOMM is not available on macOS

`RadioController.new_rfcomm()` cannot work on macOS at all: CPython there is
built without Bluetooth socket support, so `socket.AF_BLUETOOTH` and
`socket.BTPROTO_RFCOMM` are both absent (verified on macOS 26.6.2 / Python
3.12.14). `channel="auto"` additionally shells out to `sdptool`, which is
Linux-only. **On macOS, BLE is the only transport.** Linux hosts have the full
stack (`AF_BLUETOOTH`, `sdptool`, scriptable `bluetoothctl` pairing) and are
the better choice for headless or automated N76 work.

## Regions / channel banks — implemented

Each region has its own 32-channel table and a name. The unit tested
2026-09-15 (fw 147) reports `region_count = 6` and `channel_count = 32`, with
names `GMRS/MURS`, `APRS`, `GMRS`, `Weather`, `GMRS/MURS`, `Family Ops` — so
the region count is per-unit configuration, not a fixed 12. Confirmed again
2026-09-16 over RFCOMM on the same unit.

Region read *and* write are wired end-to-end on this branch:
`READ_REGION_NAME=73`, `WRITE_REGION_CH=58`, `WRITE_REGION_NAME=59`,
`SET_REGION=60`, surfaced as `RadioController.set_region`, `.set_region_name`,
`.region_names`, and `conn.write_region_channel`. `Status.curr_region` is
parsed, and `region_names` hydrates on connect.

Channel IDs restart at 0 inside every region, so a region is a self-contained
bank rather than a view onto a shared channel pool. Switching regions is what
repoints `radio.channels`; anything walking all regions must put the radio
back where it found it.

To write a whole codeplug, use `scripts/apply_codeplug.py` with a
`benlink-codeplug` plan file (see `docs/codeplug-plan.md`) rather than driving
the controller by hand — it backs up every region first and reads back what it
wrote.

## What benlink does *not* yet expose for the N76

- **DevInfo undocumented flag bits** (`_pad`). Unknown meaning; observed
  non-zero.
- **`DevInfo` capability flags are unreliable on this model.** The unit tested
  2026-09-15 (fw 147, `vendor_id=1`, `product_id=259`, `hardware_version=1`)
  reports `supports_gmrs=False`, `supports_noaa=False`, `supports_vfo=False`
  and `supports_dmr=False` — while carrying populated GMRS and Weather
  regions and sitting on 7 NOAA weather channels with `tx_disable=True`. Do
  not gate features on these bits for the N76.
- **AIS / marine channels.** N76 handles them fine; nothing benlink-specific
  needed.

## Reproducing the test session

Note that `battery_level`, `battery_voltage`, `battery_level_as_percentage`
and `position` are **async methods**, not properties — a bare `getattr` hands
back the bound method, which serializes to `{}` and looks like an empty read.
Call them: `await radio.battery_level()`.

```python
import asyncio
from benlink.controller import RadioController

# Discover this per host; peripheral UUIDs change across re-pairing.
UUID = "XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX"

async def main():
    async with RadioController.new_ble(UUID) as radio:
        print(radio.device_info)
        print(radio.status)
        print(f"channels: {len(radio.channels)}")
        for i, ch in enumerate(radio.channels[:5]):
            print(f"  [{i}] {ch}")

asyncio.run(main())
```

with this branch.
